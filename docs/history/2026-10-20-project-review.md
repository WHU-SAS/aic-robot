主要问题是目录职责、运行入口和当前状态没有形成一致结构。已验证的功能、底层参考包和历史实验被按不同阶段的项目来源拼接在一起。

## 4. 具体发现与处理建议

### 4.1 两份飞特 SDK 不能直接按文件名去重

位置：

- 原始参考：`arm/hardware/FTServo_Python-main/scservo_sdk/`
- 抓取工程使用：`car-arm/ros2_ws/src/arm_pkg/arm_pkg/scservo_sdk/`

抓取工程的 `protocol_packet_handler.py` 在读取成功路径增加了应答长度和 ID 校验：防止校验和合法但载荷长度或目标 ID 错误的包被作为有效寄存器数据使用。另有换行和空白差异。

建议：统一为一份供运行程序使用的 SDK，以当前实际使用且含校验补丁的版本为迁移基准；保留上游 MIT 许可证、来源及本地修改说明。原始参考版本可由整理前提交追溯，不能覆盖掉运行补丁。若确需同时保留上游原版与补丁版，必须明确用途和导入路径，避免随机导入其中一份。

### 4.2 两份 URDF 有真实数值差异

位置：

- `arm/robot_description/genkiarm.urdf`
- `car-arm/ros2_ws/src/arm_pkg/urdf/genkiarm.urdf`

原始参考使用 `1.57`，抓取版本部分关节原点旋转和限制使用 `1.57079632679`。不能把这些差异作为纯格式变化忽略。

完整网格在抓取工程的 `urdf/meshes/`，原始参考目录没有配套网格。建议把当前抓取使用的 URDF 和完整 STL 一起迁移到模型目录，保持其字节和语义；原始版本作为历史参考，不作为默认运行模型。

发现 `CCC.stl` 与 `CCC2.stl` 内容相同，但模型分别引用了这两个名字。不要仅为去重而删除其中一个；如需合并必须同步所有引用并验证几何，优先级低于结构整理。

### 4.3 TI SDK 与公共启动文件不应挂靠某个示例

`car/demo/02_uart1_link/build.py` 直接依赖相邻 `01_motor_encoder` 的：

- `source/` SDK；
- `keil/startup_mspm0g350x_uvision.s`；
- `keil/mspm0g3507.sct`。

建议 SDK 完整移至 `third_party/ti_mspm0_sdk/`，共享启动文件与链接脚本移至 `firmware/mspm0/platform/`。两个示例各自保留入口代码和工程文件，并显式引用共享路径。

必须同步修改两个 `build.py`、Keil 工程中的 include/library/startup/scatter 路径以及文档，不能只移动目录。

### 4.4 电机示例残留不参与当前构建的文件

当前命令行构建与 Keil 工程实际编译输入为：

- `main.c`
- `demo_control.c`
- `ti_msp_dl_config.c`
- 启动汇编
- SDK 内的 DriverLib 静态库

现有使用说明已注明原厂家 `empty.c`、`Hardware/` 仅用于对照，不参与构建。目录还存在平铺的 `ti/` 驱动副本，以及 SysConfig 辅助工具/设备包补丁。

平铺 `ti/` 与 `source/ti/driverlib/` 有 58 个同名文件，其中 45 个逐字节相同、13 个不同。这意味着不能将两套驱动随意混合。

建议先复核实际 include、工程和工具钩子：

- 未参与构建的旧 `empty.c/.h`、`Hardware/`、重复驱动和旧工具可列为归档/删除候选。
- `empty.syscfg` 具有配置参考价值；当前手工生成的配置才是编译依据。未经工具重新生成验证，不能声称二者完全可互换。
- 删除候选先留在整理前的 Git 提交中，再实施可核对的清理。
- 将真正的项目说明合并为该示例的 README，撤下当前“Empty project using DriverLib”模板作为默认入口。

### 4.5 工具归档必须检查依赖

`car-arm/k230/` 有较多 `analyze_*`、`capture_*`、`calibrate_*` 脚本，但不能只看名称判定“历史无用”。例如：

- `analyze_grasp_batch.py` 被运行相关定位代码复用；
- `download_calibration.py` 被采集相关代码导入；
- 抓取入口通过 subprocess 调用视觉程序。

建议区分运行模块、采集工具、标定工具、分析工具；同时检查普通导入、动态导入、subprocess 调用、脚本入口和数据路径，再移动或归档。

### 4.6 文档需要从历史过程转为当前可用说明

- 顶层 README 同时描述近期功能与“本次仅做仓库整合、未进行构建或真机验证”，容易让读者误解验证范围。
- `arm/docs/硬件与联调记录.md` 已达 223 行，包含整车供电、小车 UART、失败重试和纠错，不适合继续作为所有信息的唯一长文。
- `car-arm/docs/GIT_PREP.md`、迁移/审查记录描述的是独立项目导入前后某个阶段，不宜与当前操作说明同等展示。

建议：

1. 硬件说明：当前型号、引脚、供电、电平、线色和必要照片。
2. 操作指南：按 Windows 固件工具与 Linux PC 抓取环境分别编写。
3. 当前状态：验证矩阵、阻塞项、下一步，保持简短。
4. 历史记录：按日期归档测试条件、结果、关键错误与结论更正。

保留诊断事实，压缩重复重试过程；已撤回判断不能继续作为当前故障结论。

### 4.7 配置与环境边界需要显式化

当前串口默认值包含具体 Linux USB 序列号，工具链默认使用 `D:/Keil_v5/ARM/ARMCLANG/bin`。部分入口已有参数覆盖能力，整理时保留这些能力，并把设备选择与本机设置放到明确的配置或环境说明中。

`car-arm/scripts/host` 与 `scripts/vision` 为两套环境入口，依赖清单使用不同 NumPy 版本。不能在重排目录时未经验证合并环境；先使干净克隆的安装、路径和执行方式可复现。

维护 `.gitignore` 的路径规则：移动目录后原来的忽略规则可能不再覆盖构建产物、采集数据或本机依赖。必须同时检查忽略范围，避免把运行标定误排除，或把原始采集/依赖环境误提交。

| BSL/RST 排查 | 用户配合按键，120 秒内 965 次读取均 NO_ACK；未独立确认是否成功进入 BSL；未执行解锁/擦除 |
| 板卡后续安排 | 用户表示次日准备换板；截至审查未确认已经更换，不应把旧板定性为损坏 |

**注意更正：** 曾根据照片误判用户把 SWD 接到 5V/TX/RX 串口，该判断已撤回。用户明确这些针未连接，并提供上述实际线色对应。不能继续把“误接串口”作为已确认原因。

URT-2 的 TX—TX/RX—RX 是该板官方 MCU 接法，不能套用到 K230 与 MSPM0 两块 MCU 之间；后者为 TX→RX。

测试固件 HEX 当时已通过格式与地址检查，仅写 Main Flash 的 1672 字节，但编译/格式通过不等于已烧录。日志与固件位于 Windows 本机忽略提交的 `car/demo/02_uart1_link/build/`，Linux 未必拥有；保留必要摘要，不要求把所有生成文件加入 Git。
