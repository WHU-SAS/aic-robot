# 我的 AI 协作方法

我把机器人开发拆成可观察、可验证的阶段，再让 AI 在明确边界内完成实现。协作过程中，方案会随着实机结果调整，人的判断也要接受新的证据。

## 先定义行为和验收对象

我先给出使用场景：同一平台、20 mm 蓝块、约 0.5～1 米接近，再定义停车区域、尽量靠近中线、一次连续停车等要求。基础能力按直行、定角转向、视觉对准、连续接近、精定位停车、车臂协同逐步加入。

每个阶段都说明怎样算好。例如，直行的首个目标为 150 mm、允许误差 5%；停车要区分首次入窗和纠偏后入窗；抓取要区分四段动作完成、编码器判定夹住和实际物体是否夹起。数字首先是验收要求，实际是否达标还要测。

## 让 AI 解释到我能审查为止

在决定方案前，我会要求 AI 通俗解释有效控制参数、速度曲线、减速条件、同步系数、视觉处理和异常判断。对于“降一个系数”“再加一个检查”这样的建议，我继续追问它补偿的是什么、会影响哪些后续参数。

这样可以发现隐藏的假设：两轮给同样参数不保证车身走直，图像变化不一定是目标移动，软件进入搜索也不意味着能朝正确方向找回来。AI 的解释是待核对的模型，现场现象和记录用于检验它。

## 给出能够区分原因的实测反馈

我安排不同距离和转角的多组运行，说明是否平顺、有没有偏转、停后有没有再次挪动。出现异常时，尽量补充目标是否固定、有没有遮挡、是否碰过小车、使用何种供电以及是否重启。

拔掉电脑连接线可以减少牵拉，电池与适配器对照有助于排查驱动表现。固定方块的实验可以检验“目标变化”的判断。需要读日志时保留未重启的结束现场；已经归位或重启就明确说明，避免 AI 把新照片误当故障当时的状态。

这些条件不能单独证明根因，但可以排除部分解释，迫使下一步验证更有针对性。

## 多个 Agent 分工并共享接口

| 参与者 | 主要职责 |
| --- | --- |
| 我 | 任务目标、优先级、方案选择、现场测试和验收判断。 |
| 小车 Agent | 底盘、编码器、行驶停车、导航与整车调度的实现和排查。 |
| 机械臂 Agent | 机械臂运动学、舵机、准备位、抓取与恢复动作的实现和排查。 |
| 共享视觉及专项子 Agent | 定位模块、接口核对、算法改进、离线回放与独立审阅。 |

我要求跨模块复用同一视觉结果，并让不同 Agent 给方案挑刺；确定的问题由双方自行协调，无法确定的取舍再交给我。并行主要用于分析和实现，共用相机、串口和启动入口仍要协调使用，避免各自覆盖对方的程序。

## 优先保持正常流程可用

我要求静态任务快速流畅，动态恢复逐步加入。出现升级回归，先恢复原来稳定的停车，再增加异常能力；不能为了“可能有人移块”持续打断固定目标任务，也不能用不断挪车掩盖视觉失败。

取消一次纠偏上限，是为了让可恢复的任务继续推进；纠偏次数仍应尽量少。盲走轻微左偏等阶段性不足可以先记录，继续借助视觉闭环完成主要效果。这个取舍要留下边界，不能事后写成问题已经消失。

## 要求证据与结论对应

我要求 AI 展示失败原图和拟合，再解释失败原因；修改后对照旧样本，保留原始材料、配置与版本。明显坏图和正常但算法失败的图要分清，不能通过排除正常难图来提高成绩。

板端验证也分层：文件已经写入、模块能导入、零输出检查通过、真实重启能监听、实机任务成功，各自回答不同的问题。项目曾出现调试连接内监听正常、脱离调试却不可用，因此“安装成功”需要核对真正启动的程序。

## 持续追加有依据的复盘

后续案例保留四项：问题现象、我的干预、AI 的修改、验证结果。附能核对的文档或提交，记录尚未解释的现象。对同一问题的反复复现合并叙述，避免靠堆积故障次数或测试数量制造项目完成度。
